**What a 3PL can do today:** sign up, manage customers and staff, upload a customer-facing rate card (CSV/XLSX), review the detected mapping and validation, set per-service terms (DIM rules, rounding, minimums, included/waived surcharges, markup), upload zone charts, activate versions with effective dates, author and publish surcharge rules with source references and verification status, set per-customer exceptions, assign rate cards to customers, price a shipment in the calculator with an itemized, explained result, and open any customer's *Cost models* page to upload order files, run models and price shipments on their behalf (private to the 3PL until shared). **New in Milestone 4:** author versioned fulfillment fee schedules (pick and pack, packaging, kitting, labeling, receiving, storage, returns, account fees and account minimums) with a live plain-language preview of every rule, try an order against any version, activate with effective dates, assign a schedule to each customer, and see fees in the calculator, in bulk models and in forecasts they run for a customer.

**What a brand customer can do today:** sign in to the portal, price one shipment on the rate card their 3PL assigned (with plain-language explanations, no 3PL internals), save it as a scenario, upload an orders export (generic, Shopify or ShipHero-style CSV/XLSX), review how it was read and fix the mapping, keep product weights per SKU for files without package weights, run the whole file against the rate card (at today's rates or each shipment's ship date, optionally forcing one service), watch progress and resume after a reload, read the result (total, average per modeled order, what is certain vs. estimated vs. conditional, coverage, exclusions by reason, breakdowns by service / zone / weight / month / surcharge, every shipment with its lines), download the shipment-level CSV, and compare two runs. **New in Milestone 4:** read the fee schedule the 3PL assigned, see order fees for what is in the box in the calculator, answer the fulfillment questions generated from the fee schedule when running a file, read shipping, order fees, monthly charges, the account minimum and the all-in cost per order with an honest completeness label ("All-in" only when nothing the schedule prices is left out, otherwise "At least $X" with what is missing and an Add link), download per-order and monthly CSVs, forecast from assumptions without an orders file, and compare file models and forecasts.

**What is not built:** adjustment risk, PDF reports and branding, Stripe billing, carrier intelligence; within Milestone 4's area, the charges listed under *Incomplete and deferred* below (seasonal windows, weight- or value-based handling fees, discounts, fees on fees, inventory dimensions, peak-based storage, nested minimums, per-receipt sizes, return postage, forecast variants, spreadsheet import of fee schedules). The engines have been validated only against **fictional** fixtures; no real rate card, fee schedule, carrier document, customer orders export or invoice has been run through them.

## Final sweep (what it checked, found and changed)

Checked by reading and grepping the code, then by tests: every brand-facing component and route for anything that could print a rule key, rule id, version id or number, staff note or source; every fee and forecast screen and export for a default of zero on an unknown quantity; every allocated monthly figure for its basis sentence and every per-order column for allocated charges; every `"use server"` file for non-async exports and for tenant and brand resolved from the session; the carrier-buy-rate and invoice wording.

Found and fixed:

* **Two more rule keys reached the customer's page payload** as React keys (the surcharge table's `key` and the warning rows' `ruleKey` on the run page; React keys travel in the serialised page even though nothing prints them; the browser-test phase had found and fixed the same defect on the fee schedule page). Keys are now position and name (`run-results.tsx`; `modeling-lean-lists` walks the rendered tree and pins that no key is a rule key or service id).
* **A list line printed `$0.00`** when a pre-fee model had no stored total (`lists.tsx`); it now says "shipping priced for N orders" without an amount.
* **Shipping was described as "the carrier cost"** in the sentence under the view control; it is the shipping charge from the rate card, and now says so.
* **A forecast that priced only part of its volume** printed "Estimated shipping cost per order: $12.81, Forecast at 1,250 orders a month" in lists and tiles with no sign that part of the volume was unpriced. Every list line, hub tile, overview tile and comparison row now says "Only 80.00% of the volume could be priced, so this is an average over that part" (`pricedVolumeNote`; `modeling-headline`, `modeling-results`).
* **Allocated figures in a comparison had no basis of their own:** the all-in rows now open with a "Spread over" row naming the volume and period each model's monthly charges were shared over.
* **An account-minimum member whose rule is no longer on the schedule** was named by its rule key by the engine (and the key was therefore in stored summaries). The engine now names it "a rule no longer in the schedule", every screen words it "A charge that is no longer on the fee schedule" whatever name an older stored summary carries, and the brand copy of a forecast replaces it (`modeling-lean-lists`).
* **The calculator no longer stops the shipping price** when items are blank and other box fields are filled: that is a note under Items (`unitsNote`), not an error (`calculator-fees`; the e2e calculator test).
* **The lists read the whole stored summary of every run** of up to 50 projects (hub, overview and portal page). They now select only the headline inputs as JSON paths of `summary` (`SUMMARY_PARTS`), and the comparison reads its two runs whole (`loadRunsForCompare`).
* **Run setup step 2 asked today's questions whatever the run's date.** A run's own page now reads the questions for the date that run was priced for (so its "Add" links lead to a form that has step 2 when that date's version had questions), and a change of date in step 1 reads that date's questions before step 2 opens (`loadFulfillmentSetup`; `modeling-setup-date`; the browser test "choosing another date in step 1").
* **The two implementations of the completeness rule** (`headlineFigures`, `forecastHeadline`) are now tested against each other across every kind of forecast (`forecast-headline-parity`).
* **An account minimum worked out from a file shorter than 28 days with a stated volume** (a window of days, not a month) now says it was worked out from the days in the file, not from the stated volume, so at that volume the amount could be different (`MinimumView.note`).
* Mid-sentence capital in the comparison note ("Nothing left out" after a semicolon).

Not found: a non-async export in any `"use server"` file; a server action that takes its tenant or brand from the client without checking it against the session (staff name a customer, which must belong to their tenant; a brand member's argument is ignored); a per-order table or CSV column that carries an allocated monthly charge; a fee or forecast figure that defaults an unknown quantity to zero (apart from the list line above); carrier buy rates anywhere.

## Incomplete and deferred (Milestone 4)

**Not modeled by fee schedules** (design section 0; also listed to the 3PL in the editor so they are quoted outside the tool): seasonal windows inside a version (use a version per season; there are no seasonal versions); weight- or value-based handling fees; discounts and credits (amounts are zero or more); fees as a percent of another fee; per-hour special projects; inventory dimensions and per-SKU storage from dimensions; peak-based storage billing (quantities are average occupancy); nested minimums (the sets must be disjoint, at most three per version); per-receipt size lists (receipt fees assume equal receipts); return shipping postage. **Not modeled by forecasts:** delivery-area and remote surcharges (they need ZIP codes; shown as "could not be decided (up to $X)"), dependent mixes (segments), prospects without a brand record, and the "every order on service S" / "packaging X instead of Y" variants the design planned (**not built**; there is no variant code at all). **Not built:** spreadsheet import of fee schedules (rules are typed in).

**Verification gaps**

1. **Browser tests use fictional data and an emulated phone.** `tests/e2e/fees.spec.ts` and the new iPhone tests in `mobile.spec.ts` drive every new screen, but the iPhone project is desktop Chromium with an iPhone viewport, touch and user agent: no real iOS Safari check was made. The orders file in the browser is 24 rows (the 20,000-order scale is measured in unit and database tests, not in a browser). The axe checks for the new screens live in `fees.spec.ts` (the `a11y.spec.ts` file runs before it has any data to check).
2. **SQL fee arithmetic is only partly tested.** The database tests cover flat monthly rules, a long-term replace pair, a graduated monthly-volume rate, minimums and the recomputation at finish. Volume and flat-bracket tiers, tiered monthly rules, weekly and daily billing periods, returns rates and per-occurrence minimum charges are not exercised in SQL, outlier trimming of the forecast period is not tested, and no test compares `app.fee_*` with the TypeScript engine. A divergence there would make `finish_simulation_run` refuse the run (`PC003`) rather than store a wrong figure, but it would be a failed run, not a caught bug.
3. **Fee amounts are application-computed.** The database checks that an order's fee lines add up to its stored totals and that the quantities it was priced on are the file's, then recomputes totals, monthly lines, minimums and the projected monthly total; it does not recompute `rate x quantity` per order, and it recomputes only the identities and monthly charges of a forecast. A user with API access could post invented fee amounts into their **own** run or forecast (never another brand's). Same trust limit as Milestone 3, with the same planned fix (a server-held credential for the batch writer, Milestone 9).
4. **Fee engine throughput and scale are not measured.** The 0.61 ms per shipment figure is the shipping engine's. The fee step adds work to every window; a 20,000-order run with fees, and a forecast at the 1,500-cell limit, were not timed.
5. **Real data.** Every fee, rule, scenario and forecast in the tests is invented. No real fee schedule, contract or invoice has been used.

**Residual gaps after the final sweep** (each is real; none is hidden by the figures shown):

* **Identifiers a brand's own members can read through the API.** The pages and files the app builds print no rule key, rule id, version number, staff note or source, but the database does not hide the first three from a brand's members: `fee_rules.key` and ids, version numbers and pinned version ids are readable for the schedule assigned to them, and their runs' stored `summary` (fee `completeness` rules, `byRule` keys, minimum members' `ruleKey`, monthly lines' `ruleKey` and `driverKey`, the provenance version ids) and `reference_data` (`feeDictionary` rule ids and keys, engine versions) carry them. Staff-only notes and sources are not readable by a brand. A staff-only copy of the keys and versions (a table brands have no policy for) would be the fix; the schema was not changed in this sweep. This falls short of "nothing confidential reaches brand users" at the API, not at any screen or file.
* **Question (driver) keys travel to the customer's browser.** Answers are posted by the question's key, so the key is in the run setup form's state, the forecast form's state and the response of `loadFulfillmentSetup`; no screen, accessible name or export prints it. A 3PL that gives a driver the same key as a rule would make that rule's key visible there.
* **Summaries stored before the final sweep** hold the rule key as the name of an account-minimum member whose rule had gone from the schedule (screens and the brand copy of a forecast replace it; the stored JSON still has it, and it is part of the first item).
* **Run setup and dates.** (i) A customer whose schedule has no version in effect **today** gets the one-step form with no step 2 even when the date they choose has a version (a model's own page does read its own date; a new run from the orders page does not). (ii) The database pins the latest earlier version for the monthly charges when none is in effect on the monthly date; `brand_fee_schedule_on` does not, so for such a date step 2 says there are no questions while the run's monthly charges are priced from the earlier version with no answers ("no number was given"). (iii) With rates read on each order's ship date, the questions are those of the version in effect at the end of the file's period (the version the database validates the answers against); an order priced under an earlier version whose rule asks a question the later version does not ask has no answer for it, and that charge is "not computed" for the order. (iv) The date change in step 2 is covered end to end in a browser, not by a unit test of the hook.
* **Account minimum on a short file.** The minimum is worked out month by month from the orders' dates. For a file of fewer than 28 days with a stated volume, that is a prorated window of the file, not an average month at the stated volume, and its top-up can differ from the shortfall at that volume (the design's section 4 and 5 as written); the card now says so. A different evaluation (an average month at the stated volume) would need the SQL recomputation changed too.
* **Two implementations of the completeness rule** remain (`headlineFigures` and `forecastHeadline`); they are tested against each other, not merged.
* **Comparisons and the saved-forecast page read whole summaries** (two runs, one forecast); the lists read about the headline inputs only, which still include each run's fee `completeness` and `monthly` (a few kilobytes a run). The lean select was exercised against the small local database only, not timed against 50 large projects.
* **Wording of event charges.** The rule sentence for monthly drivers reads "$12.00 per pallet per month" for receiving and "$3.00 per return per month" for returns, which is exact for storage and can be misread for charges that happen once per pallet or return (`describeMonthlyRate`). It is wording, not an amount; the tests do not pin the suffix.
* **Storage line with a long-term rule.** The storage line shows the derived quantity ("8 pallets × $18.00", the 12 typed minus the 4 held long-term) and the long-term line shows 4; both are correct and the explanation says what each is.

**Other limits**

* Representative ZIP per zone: the forecast engine can price a zone with a supplied ZIP (`deps.destinationZipForZone`), but the application never supplies one, so every forecast is priced by zone and ZIP-dependent surcharges stay undecided.
* Runs are still client-driven (no worker), as in Milestone 3.
* A model priced before this milestone keeps its version 1 summary: it shows its shipping line and says to run it again for fees. A run that was in progress during the migration fails with a "started by an older release" message.
* New per-user, per-hour rate limits: creating a fee schedule 60, forecast previews 240, forecast saves 120, forecast form context loads 600, calculator box options 1,200, run setup questions for another date 600 (`modeling.setup`). Other fee-schedule edits and the "try an order" panel are not rate-limited beyond the permission and the database's own checks.

## Design decisions made in Milestone 4 (say so if you disagree)

These are the decisions recorded in the design contract's section 10, as implemented and tested.

* **`rounding` lives on the version** (editable while draft, pinned by the snapshot), not on the schedule. A schedule's `description` is customer-visible like its name; staff-only text exists only in notes and sources.
* **Line-derived quantities:** `lines` is the order's lines with units above zero and is null when there are none; `distinctSkus` is the distinct non-null SKUs and is null when `lines` is null or any counted line has no SKU. An assumed `lines` or `skus` is accepted only where the derived value is null, an assumed `units` only where the file has none. The batch input and `advance_simulation_run` read one SQL function.
* **Fee date per order** is the as-of date (fixed-date basis) or the order date, else its first ship date; `advance` checks it. `fee_rates` is keyed per version id and resolved at start for every version the run may price with. Monthly-volume tiers are allowed only on the bases order, unit, package and shipment, priced per unit; monthly units, packages and shipments are derived from the in-period population scaled to the volume.
* **`projected_monthly`** is recomputed in `finish_simulation_run` (totals scaled to the volume at 80 % coverage or better, else the period average, plus monthly charges and an exact top-up, rounded once) and must agree with the summary's monthly total within one cent. `allocate` computes monthly figures as (total x V) / modeled orders.
* **Minimums in SQL** (`app.run_minimums`): the fee dictionary comes from `reference_data` (validated before and stored after); every per-rule per-month sum is rounded to cents once and scaled by coverage first when a month is not fully modeled; undated processing orders make every minimum an upper bound; no month profile gives `not_computed`; a version with no minimum rule is `none`, treated as an exact zero top-up.
* **Forecast carve-out:** a flat `month` rule stays definite in forecasts; `save_forecast_run` checks that shipping and processing are not definite and recomputes the monthly lines from the answers.
* **Order content for files without item counts:** `fulfillment.orderContent.rows[{units, lines, sharePct}]`, assigned by a deterministic largest-deficit apportionment of the order ordinal over the cumulative shares (6/4 exactly for 60/40, 5/3/2 for 50/30/20; within one order of every share at every prefix). It depends only on the ordinal, so batch splits do not change it, and SQL never recomputes it. Averages are turned into two rows by the form.
* **The run action canonicalises `assumptions`** (sorted keys, canonical decimal strings, empty objects dropped) so an identical resubmission attaches to the live run instead of failing with "different settings".
* **Headline rule (F1):** when a minimum is an upper bound only because of coverage or undated orders, no category is not-modeled; the headline reads "at least $Y" with "the minimum could add up to $X" from the allocation caveats and the minimum's reasons. `not_computed` means "no month buckets", never "no member modeled".
* **SQLSTATE classes:** `PC001` invalid input, `PC002` stale or incompatible client state, `PC003` does not reconcile. `advanceRun` treats any code starting with `PC` as permanent and fails the run; the batch core checks the partial's version before folding.
* **Per-run cap:** the fold keeps at most 50 distinct `packaging:<type>` unresolved rows; further types collapse into one "other types" row.
* **Monthly version fallback:** when no version is in effect on the monthly date but an earlier one started on or before it, `start_simulation_run` pins the latest such version for the monthly components and the provenance shows its dates; orders are still pinned per fee date (`not_effective` where nothing covers them).
* **Refusals:** `advance_simulation_run` rejects a window whose order results name an order twice (`PC003`, never a unique-key error a client would retry); `save_forecast_run` refuses a `minimumStatus` that disagrees with whether the version has a minimum rule.
* **Forecasts price by zone**, not by a representative ZIP, so ZIP-dependent surcharges stay "could not be decided (up to $X)".
* **Order-share drivers in forecasts are expected values:** a qualifying order is charged max(0, count - allowance) x rate and the expectation is the share times that, so "40 % of orders get 4 inserts, the first free" costs 0.40 x 3 x $0.25 = $0.30 per order.

Where the code differs from the design text and the tests follow the code: the driver kinds are `monthly_quantity`, `order_share` **and `returns_rate`**; the fee statuses include `skipped` (not "unmodeled") and the run volume basis includes `none` (no stated volume and a file too short to derive one); a brand can read **archived** versions of its schedule (not only active ones) so that history stays explainable; `calculateMonthlyFees` takes `(answers, schedule, monthlyOrders)`; `ForecastSummary` is version 2 and `save_forecast_run` takes a `p_pins` argument; any month with incomplete coverage makes a minimum an upper bound (while still scaling its counted amounts), not only coverage under 80 %.

## Honest limitations and gaps (Milestone 3)

1. **Fictional data only.** The orders fixtures (`tests/fixtures/modeling`) are invented, as are the rate card, rules and zone chart they are priced against. No real customer orders export has been imported, and no result has been checked against a real invoice. Until that happens, modeling output demonstrates mechanics, not prices.
2. **The page must stay open while a model runs.** Runs are driven by the browser calling a time-boxed server action in a loop (durable cursor in the database, idempotent windows, resume after reload or network loss, pause detection after two minutes without progress). There is **no background worker**: closing the tab pauses the run until it is reopened; a 20,000-order file takes on the order of a few minutes of open page. The batch core is written so a worker (cron or queue) can call it without changing the pricing path; that is the production step planned for Milestone 9.
3. **Scale was measured, not driven end to end.** Engine throughput is 0.61 ms per shipment in the unit test; the database functions and the fold are tested on small sets; the browser journey runs a 24-order file. A real 20,000-order run in a browser has not been exercised.
4. ~~No manual forecasting yet.~~ Superseded: forecasts from assumptions were built in Milestone 4.
5. **Order-file formats** are detected heuristically (generic, Shopify, ShipHero-style). Other WMS exports fall back to manual column mapping in the wizard; multi-sheet workbooks use the first sheet that looks like orders. Only US destinations are modeled; international rows are excluded with a reason. Multi-package shipments need a package/shipment column or one row per package.
6. **Product weights** are a flat per-SKU list (weight and optional dimensions) applied as one package per shipment summed over line units; kitting, cartonisation and multi-box rules are not modelled, and the result says every such weight is an assumption.
7. **Results are kept indefinitely** and files are stored as bytes in PostgreSQL under RLS (15 MB cap). No retention policy, malware scanning or object storage yet.
8. **Rate limits** (per user, per hour, PostgreSQL-backed): 30 uploads, 20 preparations, 60 run starts, 3,000 batch calls, 120 scenario saves; calculator 600.
9. **Adversarial code review was run and acted on.** Three reviewers (authorization, data-path correctness, customer UX/honesty) produced 81 findings, each checked by a skeptic. ## Design decisions made in Milestone 3 (say so if you disagree)

* **A modeled order is one that is not cancelled and every one of whose shipments priced.** Averages are per modeled order; coverage states what share of the file that is; cancelled and unpriceable orders are counted by reason, never silently excluded from the denominator.
* **Exposure is never averaged.** Conditional charges ("may be added after shipping") and unresolved amounts are shown as "up to" totals and counts, never folded into the average cost per order.
* **Defaults are assumptions and say so.** A residential default, a default origin ZIP or a product weight make the dependent charges *estimates* and the run reports how many shipments relied on each.
* **Pricing basis is explicit**: at today's rates (one as-of date for the whole file) or at each shipment's ship date; runs pin the exact versions used per ship date.
* **Trusted figures are recomputed in SQL.** The headline totals and counts a customer sees come from the stored results, not from a summary the client sent.
* **Staff-prepared models are private until shared.** A 3PL can prepare and iterate on a customer's behalf; the customer sees nothing until *Share with customer*.
* **Brand-facing output carries no 3PL internals**: fixed label for the rule set, codes and ids only in storage, names and plain language in the UI and CSV, whoever ran the model.
* **Rejected review finding:** storing the full engine line explanations per shipment; lines are re-derived from the dictionary and codes on demand, which keeps a 20,000-shipment run small and reproducible.
* **Rejected review finding:** moving the batch writer behind a service-role credential now. The app deliberately holds no credential a signed-in user lacks (every query runs under the user's own JWT), so `advance_simulation_run` is callable by the user. What it accepts is now tightly checked (own rows only, exact windows, reconciled totals); a server-side worker credential is planned for Milestone 9 and SECURITY.md states the gap.
* **Rejected review finding:** stripping rule keys and version ids from the stored run dictionary. They are identifiers, not notes; keeping them is what makes a run reproducible for the 3PL. The data a customer must never see (source notes, exception references, verification vocabulary) is removed at the source instead.
* **A per-line, per-unit grams column (Shopify "Lineitem grams") is not a package weight** and is no longer mapped as one; such files are priced from product weights.

## Design decisions made in Milestone 2 (say so if you disagree)

* **Fuel and other percentage rules cover shipment-level charges even when configured per package** (one shipment-level line over counted shipment-level surcharges). A per-package rule never silently exempts a shipment-level surcharge from fuel.
* **Exclusivity is resolved before bundling, to a fixed point**; a waived rule that would otherwise have won its group stays visible as *waived*; an unknown higher-priority member stays listed as an uncounted estimate and the winner's explanation says the charge may be replaced.
* **Rule-imposed billable-weight floors** apply only from rules that survive conflict resolution; conditions are evaluated on the package before any floor.
* **Reported weights** are exact when they terminate within 12 decimals, otherwise rounded up at the 12th decimal, so a reported billable weight never falls below what was priced; the UI formats for display.
* **A counted line from an unverified rule is an estimate**, never definite; a percentage of an estimated base is an estimate.
* **Customer exception modes**: exclude, override amount, override percent, markup percent, add percentage points; at most one live exception per rule per customer on any date (database-enforced).
* **Service markup** ("published + X%") scales charged surcharges unless a customer exception replaces the figure.
