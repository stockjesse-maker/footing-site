# Pricing engine

`src/engine` is a pure, deterministic TypeScript library: no I/O, no clock, no randomness, no framework imports (enforced by an ESLint rule). It prices one shipment against a **customer-facing** rate card and the surcharge rules in force on the ship date, and returns an itemized result that always adds up and always says what it does not know.

> **Status:** implemented and tested against an independently derived golden dataset of 32 fictional scenarios plus per-area unit tests. **Not validated against real carrier/customer examples yet**: no real rate card or carrier surcharge document has been run through it. It must not be called production-ready until that happens (see IMPLEMENTATION_STATUS.md).

## Hard rules (and where they are enforced)

| Rule | Enforcement |
|---|---|
| Base shipping price comes only from the 3PL's customer-facing rate card | The engine has no other price input; the schema has no column for a buy rate |
| No fabricated surcharge amounts or customer prices | No amounts in code or seeds; every rule version records `source_reference`, dates and `verification_status`; fixtures are labelled fictional |
| Missing rate → explicit *unavailable*, never extrapolated | `lookupRate` returns `no_rate_for_weight` / `no_rate_for_zone` / `no_rate_for_origin` |
| Definite / estimated / conditional charges are never mixed silently | Every line carries `chargeClass` and `counted`; totals are split |
| No double counting of bundled or mutually exclusive surcharges | Exclusivity groups, `excludesRuleKeys`, included/excluded keys on service terms |
| Reproducible history | Results reference rate-card version, terms version and every rule key@version |

## API

```ts
import { calculateShipment } from "@/engine";
const result = calculateShipment(input, { rateCard, rules, zipLists, overrides });
```

Types are in `src/engine/types.ts`. All money and weights are decimal strings; arithmetic uses decimal.js (precision 28, HALF_UP where rounding is explicit). Line amounts are rounded to cents **once, when the line is created**; totals are sums of rounded lines.

## Calculation pipeline

1. **Validate** (`validate.ts`, Zod): positive weights, all-or-none dimensions, 5-digit ZIPs (ZIP+4 accepted and trimmed), a real calendar date, 1–200 packages, ZIP or zone. Invalid → `status: "unavailable"`, reason `invalid_input`, with messages. The engine never throws for data problems.
2. **Rate-card effectivity**: `effectiveDate ≤ shipDate ≤ expirationDate` (inclusive) or `rate_card_not_effective`.
3. **Service**: `(carrierCode, serviceCode)` must be on the card → else `service_not_on_rate_card`.
4. **Billable weight per package** (`dim.ts`): actual weight → lb; round each dimension per `dimensionRounding`; cubic inches; if a `thresholdCubicIn` is set, DIM applies only above it; DIM lb = cubic ÷ divisor (exact decimal); compare **unrounded** actual vs DIM; apply the service `minBillableLb` and any **rule-imposed floor** (a per-package rule with `billableWeightFloorLb` whose conditions depend only on the package: dimensions, actual weight, type, flags; e.g. a large-package minimum billable weight; exclusivity between such rules is resolved first and the highest surviving floor applies); round the winner per `weightRounding` (`up_whole_lb`, `up_whole_oz` = next 1/16 lb, `postal` = ounces below 1 lb then pounds, `none`). Exempt services use actual weight. If dimensions are missing or the card states no divisor, the engine prices on actual weight, classes **that package's** base line **estimated**, and warns (`dimensions_missing` / `dim_divisor_missing`), even when a minimum or floor then raises the weight.
5. **Zone** (`zones.ts`): `zoneIndependent` services use zone `ALL` and skip resolution. Otherwise the zone entered directly (normalized: trimmed, upper-cased, "Zone 5" → "5"), or the service's zone chart (`zoneChartKey`, "default" for single-chart cards): candidate rows are ordered longer origin prefix first, then longer destination prefix, then narrower range; a destination matches when its first N digits fall within `[destPrefixFrom, destPrefixTo]`. None → `zone_unresolved` (+ `zone_chart_missing` warning if the card has no chart for that key/carrier); equally specific rows naming different zones → `zone_ambiguous` (the database also forbids overlapping ranges on an activated card).
6. **Base rate per package** (`rates.ts`): rows for the service and **zone** first (`no_rate_for_zone` names the zones covered), then the most specific origin scope among them (5-digit > 3-digit > any-origin; an origin-priced zone with no match → `no_rate_for_origin`), then the bracket with `weightMin < w ≤ weightMax` compared in the row's unit (`no_rate_for_weight` states the heaviest bracket and that rates are not extrapolated). Minimum charge = max(row, service) → a separate `minimum_charge` line for the difference, carrying the base line's class.
7. **Surcharge applicability** (`surcharges.ts`, `calculate.ts`): candidate rules = carrier matches, service listed or null, effective on the ship date, one rule per key (a tenant rule shadows a platform rule with the same key; then the highest version), not in the service's `excludedSurchargeKeys`. Conditions are ANDed (`any_of` groups are ORed); each evaluates to *applies*, *not*, or *unknown* (needed input missing: dimensions, destination ZIP, zone, or a ZIP list not loaded for the date). Conditions are evaluated on the package as measured **before** any rule-imposed floor, so floors never feed back into applicability. Absent optional inputs (no declared value, no signature option, no flags) mean *not applicable*. Per-package rules evaluate per package; per-shipment rules evaluate once (greater-than tests hold if any package satisfies them, less-than-or-equal only if all do). Rules with a `rule_applied` condition are evaluated in a second pass once every other rule's fate is known: the companion of an *unknown* parent is itself *unknown* (listed, not counted), a per-package companion of a per-shipment parent applies on every package, and a rule depending on another dependent rule is skipped with warning `rule_reference_cycle`. **Exclusivity, then bundling, to a fixed point**: within each exclusivity group (per package), among the members that apply and are neither waived nor bundled away, the highest priority wins (ties → larger computed amount → key order); other applying members are dropped, except a waived member that would have won, which stays visible as *waived* because the waiver is what changed the bill. Unknown members are kept as uncounted estimates; when one outranks the winner, the winner's explanation says the charge may be replaced. Then, starting from every surviving applying rule, the keys in its `excludesRuleKeys` are bundled away transitively (per-package rules only within their package); because bundling can remove a group winner, the two steps repeat until nothing changes, so the outcome never depends on key spelling or evaluation order. Waived and unknown rules never win a group or bundle anything. Billable-weight floors (`billableWeightFloorLb`) are applied only from the per-package rules that survive, after which the package is re-measured and re-priced.
8. **Line status and class**: `charged` (counted), `included` (bundled into the base under the customer terms), `waived` (customer `exclude` override, warning `rule_overridden`), `conditional` (post-shipment adjustment, never counted), `unknown` (could not be decided; shown as an **estimate**, not counted). A counted line from an `unverified` rule is classed **estimated**, never definite (warning `unverified_rule_applied`).
9. **Amounts, in three phases**: flat and per-unit rules; then percentage rules other than fuel, over the phase-1 lines; then fuel over every counted non-fuel line. `per_unit` = amount × ceil((declared value − free allowance) ÷ unit size) per package, at least `minimumCharge`. Base kinds: `base_rate` (base + minimum lines), `base_plus_all_surcharges`, `base_plus_categories`. Percent rules are computed per package (one line each) plus one shipment-level line over the counted shipment-level charges, whether the rule is configured per package or per shipment, so a shipment-level surcharge never silently escapes fuel; the shipment-level line is omitted when its base is zero. A percentage of an estimated base is itself **estimated**. Customer overrides: `override_amount` / `override_percent` replace the figure; `markup_percent` scales the published amount or percentage; `add_percent_points` adds points to a percentage. Without an override, the service's `surchargeMarkupPercent` ("published + X%") scales every charged surcharge.
10. **Totals**: definite = Σ counted definite lines; estimated = Σ counted estimated lines; expected = definite + estimated; conditionalExposure = Σ conditional lines; unresolved = Σ unknown lines (neither in expected).
11. **References and warnings**: `engineVersion`, rate-card version, terms version, every rule key@version with scope/source/verification, the ZIP-list versions used, and the overrides applied; multi-package shipments are priced package by package and the whole shipment is *unavailable* if any package cannot be priced (no partial totals).

Line order in results: per package (base, minimum, surcharges in the carrier's category order), then shipment-level lines, fuel last. Consumers must not depend on order. All ordering inside the engine uses code-point string comparison, never locale collation, so results are identical on every runtime.

Reported weights (`actualLb`, `dimLb`, `billableLb`) are exact when they terminate within 12 decimals and otherwise rounded **up** at the 12th decimal, so a reported billable weight never falls below the value that was priced (and never outside its bracket, whose minimum is exclusive). Display formatting is the UI's job.

## Assumed inputs (engine 2.2.0)

Bulk modeling often has to fill in what an orders file lacks. `ShipmentInput.assumed = { residential?, originZip?, weight?, dimensions? }` tells the engine which inputs came from an assumption (a default, a product weight) rather than the record. Every counted charge that rests on an assumed input is classed **estimated** and says so in its explanation: the base rate when weight, dimensions or the origin (hence the zone) were assumed; surcharges whose conditions read the residential flag, the zone, or the package measurements; percentages over those lines follow automatically. The result carries an `assumed_inputs` warning. Nothing about the amounts changes; only their certainty does.

## Bulk modeling (`src/engine/modeling`)

A run prices each shipment of an orders file with `calculateShipment` and stores a compact result (`encodeResult`: dictionary-encoded lines `[entry, cents, status, class, package]`, split totals, billable weights, warning codes). `foldBatch` accumulates whole orders into a `PartialSummary` (totals, by zone / service / billable-weight bracket / month / surcharge, exclusions by reason, assumptions, warnings) and `finalizeSummary` turns it into the customer-facing `BulkSummary` (averages HALF_UP to cents or null, coverage and shares to one decimal). Rules: an order is **modeled** only when it is not cancelled and every one of its shipments priced `ok`; totals, averages and breakdowns cover modeled orders only; conditional exposure and unresolved amounts are reported as "up to" figures and never averaged. Everything is decimal strings; nothing is summed in floating point. Since Milestone 4 the fold is version 2 and also folds each order's fees (see *Fulfillment fees* below and ARCHITECTURE.md). Tests: `tests/unit/modeling-fold.test.ts`.

## Fulfillment fees (`src/engine/fees`, Milestone 4)

A second pure engine prices the 3PL's own fulfillment charges (pick and pack, packaging, kitting, labeling, receiving, storage, returns, account fees) from a **fee schedule**: a versioned, customer-facing list of rules the 3PL typed, like a rate card. It has no I/O and no framework imports (same ESLint rule), `FEE_ENGINE_VERSION` is `1.0.0` and is stored with every run, and it never reads or produces a carrier buy rate. Like the shipping engine it has been verified only against **fictional** fixtures: no real fee schedule, contract or invoice has been run through it.

| Rule | Enforcement |
|---|---|
| Every amount is one the 3PL typed; nothing is defaulted, seeded or extrapolated | Amounts are columns of `fee_rules` (non-negative, up to four decimals); fixtures are labelled fictional; a rule with no amount for a situation simply does not charge |
| An unknown quantity is "not computed", never $0 | `calculateOrderFees` lists a rule whose input is unknown and not assumed in `unresolved` with a reason; an unanswered monthly question is `notModeled` with its rate; no line is created for either |
| Estimates are never definite | Each line is classed `definite` (every input came from the file or the schedule) or `estimated` (an assumed input, a pinned volume rate, an order driver, a percentage of estimated shipping) |
| Monthly charges are allocations, never per-order fees | `calculateMonthlyFees` and `allocate` keep them apart from order-scope lines; no order result carries a monthly amount |

### Rule model

A rule is one customer-facing charge of one version: `key` (slug, unique within the version, never shown to customers), `name`, `category`, `description` and `helpText` (both customer-visible; the help text is what the 3PL tells the customer about answering the rule's question), `position`, and:

* **`scope`**: `order` (computed per order from that order's data) or `monthly` (computed per month from stated quantities).
* **`basis`**, which fixes what one unit of the charge is. Order scope: `order` (1), `unit` (the order's item count), `line` (order lines with units above zero), `sku` (distinct non-null SKUs among those lines), `package`, `shipment`, `shipping_percent` (a percentage of the order's shipping) and `order_driver` (a per-order quantity the customer states as a share of orders and a count: inserts, kits, labels). Monthly scope: `month` (flat, quantity 1), `driver` (a stated monthly quantity: pallets stored, bins, cubic feet, units stored, pallets or cases received, receipts, returns...) and `minimum` (an account minimum).
* **`method`**: `flat` (amount x chargeable quantity), `tiered`, `percent` (only `shipping_percent`) or `minimum` (only `minimum`). `percentBase` is `shipping_total` (counted definite and estimated shipping lines; conditional and unresolved amounts never) or `base_freight` (the base-rate and minimum-charge lines only).
* **`tiers`**: `{on, mode, pricing, brackets}`. `on` is `order_quantity` (this order's chargeable quantity) or `monthly_quantity` (the month's total of the rule's basis). `mode` is `graduated` (each bracket priced at its own rate over the part of the quantity inside it) or `volume` (the whole quantity at the rate of the bracket it falls in; with `pricing: "flat"` that bracket's amount is the whole price). Bracket *i* covers (upTo[i-1], upTo[i]]; the last bracket is open-ended; at most 50. A quantity of 0 costs 0. A tiered rule has no free allowance: model one as a first bracket at 0.
* **`includedQuantity` / `includedPer`**: a free allowance of `includedQuantity` x the count of `includedPer` (`order`, `line`, `sku` or `shipment`; null means once per order or month). Chargeable quantity = max(0, quantity - allowance). "First pick included" is basis `unit` with 1 included per order; "first unit of each line free" is 1 included per line; "additional packages" is basis `package`, 1 included per order. The editor offers these as presets. If the count an allowance reads is unknown, the rule is not computed.
* **`minimumCharge`** (per occurrence: an order, or a month): replaces a smaller computed amount, only when the chargeable quantity is above zero.
* **`conditions`** (order scope): `minUnits`/`maxUnits`, `minLines`/`maxLines`, `minPackages`/`maxPackages` (inclusive) and `packagingTypes`. A condition that reads an unknown quantity makes the rule not computed.
* **`exclusiveGroup` / `priority`**: rules in one group compete; the lowest priority that applies is charged and the others are listed as "replaced by ...". For per-package rules the competition is per package, and a rule's quantity counts only the packages it won.
* **`driver`**: `{key, label, unit, kind, billingPeriod?, longTerm?}` (below). Several rules may share a driver key on purpose: the question is asked once.
* **`minimum`**: `{amount, appliesTo: {categories, includeRuleKeys, excludeRuleKeys}, includesShipping}`, resolved at activation to `resolvedRuleKeys` (below).
* The schedule version's **`rounding`**: `invoice_line` (default) or `transaction`.

What a schedule cannot say is shown to the 3PL in the editor ("What fee schedules cannot model yet") and listed in IMPLEMENTATION_STATUS.md.

### Packaging

A package's type is normalised (trimmed, lower-cased, runs of spaces, underscores and hyphens collapsed to one space) by one function in the engine and one in SQL. A package matches a rule when its type equals one of the rule's `packagingTypes`, or the rule lists `"*"` and the package has a type. A package with no type uses the run's packaging default when the customer chose one (every packaging-conditioned line is then an estimate and the result carries `packaging_defaulted`); otherwise every packaging-conditioned rule is not computed (`packaging_unknown`). A type that no packaging rule matches (and there is no catch-all) is reported once per distinct type as `packaging:<type>` / `packaging_unmatched`, but only when the schedule has at least one packaging-conditioned rule. Two rules pricing the same type must share an exclusive group; activation refuses anything else.

### Drivers: stated quantities and per-order shares

* **`monthly_quantity`** (pallets stored, cubic feet...): the customer states an average monthly quantity. `billingPeriod` `week` or `day` converts it with 30.4375 days a month (a week is 30.4375 / 7). A flat rule charges quantity x rate; a tiered rule reads its brackets over the monthly quantity; `minimumCharge` applies when the quantity is above zero.
* **Long-term storage** (`longTerm: {mode, replacesRuleKey, thresholdDays}`): `replace` takes the long-term quantity out of the standard rule's quantity and bills it at the long-term rate (12 stored, 2 long-term at $18 and $25 is 10 x $18 + 2 x $25); `surcharge` adds the long-term charge on top of an unchanged standard quantity. A long-term answer larger than the stored quantity is an input error (the form, `app.validate_fulfillment` and the forecast pre-flight refuse it; the engine throws). The long-term rule must use the same unit and billing period as the rule it refers to.
* **`returns_rate`**: the customer states how many of every 100 orders come back (0-100); the monthly quantity is monthly orders x rate / 100, it scales with volume, and it needs the monthly volume (without it the rule is `notModeled`, reason `volume_unknown`).
* **`order_share`** (inserts, kits, labels): an answer is `{sharePct, countPerOrder}`. With p = sharePct / 100, order ordinal *i* qualifies exactly when floor(i x p) > floor((i - 1) x p), and a qualifying order has `countPerOrder` of them (the allowance then applies to that count). Because it depends only on the ordinal, splitting a run into batches never changes which orders qualify. Lines from order drivers are always estimates.
* **Receiving** questions are labelled by the service they price and are never prefilled from shipped volume.
* A question the customer did not answer leaves its fee not modeled (shown with its rate and an "Add" link). "Not sure, leave it out" and an unanswered blank are the same; "We don't use this" is an explicit "0" and models the fee at zero.

### Minimums and allocation

An account minimum is evaluated per calendar-month bucket *m* with covered fraction *f* (RULES.md C): what counts is the sum, over the rules in its resolved set, of each rule's monthly total rounded to cents once (an order rule's charges on the orders dated in the month; a monthly rule's amount x *f*), plus the customer's expected shipping when `includesShipping`; the month's minimum is amount x *f*; the top-up is max(0, minimum - counted); the run's top-up is the sum over months. The resolved set is every rule except minimums and flat `month` rules that matches the categories (an empty list means all), plus included keys, minus excluded keys; a version has at most three minimums and their sets are disjoint, so a top-up never feeds another minimum.

Status is `exact` only when every member is modeled for every order of every month and coverage is complete. `upper_bound` means "up to": a member is not modeled, a rule is unresolved on a processing order, an order has no date, or some month has fewer modeled orders than the customer shipped in it (that month's counted amounts are then scaled by shipped / modeled, **and** the result is still flagged `upper_bound`). An upper bound is shown ("the account minimum could add up to $X a month") and is **never** added to an all-in figure or a projection. `not_computed` means no calendar month is known (no order in the file has a date). A version with no minimum rule has status `none`, treated as an exact zero top-up. A member of a minimum's resolved set whose rule is not in the schedule (a stored key with no rule) is reported with the state `not_in_schedule` and the neutral name "a rule no longer in the schedule": its key is its identity inside the engine and never its name, because names are stored in summaries and printed by customer screens (customer screens word it "A charge that is no longer on the fee schedule" whatever a stored name says). The minimum is evaluated over the days of the calendar months the orders fall in: for a file shorter than 28 days that is a prorated window of the file, not an average month at a stated volume, and the results card says so (IMPLEMENTATION_STATUS.md, residual gaps). (The design text scaled months at 80 % coverage or better and called only lower coverage an upper bound; RULES.md C3 and the code flag every incomplete month, and they are what the tests derive from.)

`allocate` turns totals into figures over the customer's real monthly order volume *V* (never over the modeled orders alone): monthly shipping and processing are (total x V) / modeled orders when the processing orders are at least 80 % of the population, else the period's own total over its months ("at least", with a caveat); monthly fixed charges are exact; the monthly total is their sum plus an exact top-up, rounded once; allocated per order is (fixed + top-up) / V, all-in per order is monthly total / V, annual is the exact monthly total x 12 rounded once ("if every month looked like this"); a rounded average is never multiplied again; with no volume or V = 0 the per-order figures are null and the fixed charges are still listed.

### Money, rounding and classes

Fee line amounts are integers of ten-thousandths of a dollar (E4) so $0.0125 per unit is exact; decimal arithmetic is exact and a result is rounded once. With `invoice_line` rounding order lines stay at E4 and totals are rounded to cents once when reported; with `transaction` rounding each order line is rounded HALF_UP to cents. (Monthly lines are always exact E4; transaction rounding applies to order lines.) $0.0125 x 7 units x 20,000 orders is $1,750.00 exactly under `invoice_line` and $1,800.00 when each order's $0.0875 rounds to $0.09. Every aggregate shown to a customer (per rule, per month, per order average, monthly total, annual) is one HALF_UP rounding of an exact figure.

An order's fee result has `status` `ok` (every applicable rule computed), `partial` (some line computed and some rule not) or `no_content` (nothing could be computed); `definiteE4` and `estimatedE4` sum the lines by class. In a run the result also gets a fee status (`no_schedule`, `not_effective`, `date_missing`, `skipped`) when the fee engine could not or should not run, and only orders that are shipping-modeled and `ok` or `partial` count as *processing orders*.

### Monthly-volume tiers (pinned rates)

A rule tiered on `monthly_quantity` prices every order with one effective rate resolved once per run from the monthly total of its basis (orders, items, packages or shipments): graduated brackets give graduated(Q) / Q rounded to E4, volume brackets the rate of Q's bracket. The rate is pinned on the run (`fee_rates`, per version id) and every line it prices is an estimate. Without a pinned rate (no volume) the rule is not computed (`assumption_missing`). Example from the golden set: at 3,000 orders a month, $3.00 for the first 1,000 and $2.50 after is $2.6667 an order and $8,000.00 in total; as volume pricing the same quantity is $2.50 an order and $7,500.00.

### The exact rules, and where they come from

`tests/fixtures/fees/RULES.md` restates the design contract precisely enough to compute every scenario by hand, and the golden expectations are derived from it, never from the code: A1-A10 (allowances, conditions and packaging, exclusive groups, amounts and tiers, zero quantities, percent of shipping, order drivers, charge class, rounding, the result and its status), B1-B4 (monthly rules, long-term replacement, returns rates, unused answers), C1-C4 (minimums), D1-D7 (allocation and caveats) and E (pinned monthly rates). Where the code and the design document differ in wording or signatures (the monthly entry point takes `(answers, schedule, monthlyOrders)`, the driver kinds are `monthly_quantity`, `order_share` and `returns_rate`, `rounding` belongs to the version), RULES.md and the code are what the tests and this page follow.

### The golden derivation process

1. The rules were written down first (RULES.md), from the design document and before the engine.
2. The fictional schedules (`schedules.json`: a standard schedule, line-based, tiered, storage with long-term, transaction and invoice-line rounding, a minimum that counts shipping) and scenarios (`scenarios.json`: 22 order scenarios, 9 monthly/minimum/allocation scenarios, 4 pinned-rate scenarios) were written with invented amounts.
3. `expected.json` was derived by hand from RULES.md and the fixtures by two independent derivers and reconciled scenario by scenario, without reading the engine code (as the file's own header records). Where RULES.md was silent and both derivers made the same call, the call is written in the file's header; the one disagreement between them was a representation of a non-terminating quantity string (not a value), recorded in `_disagreements`, and the test compares that quantity numerically.
4. `tests/unit/fees-golden.test.ts` runs every scenario against the engine (35 tests) and also checks that no line explanation prints a rule key.
5. A new behaviour gets a scenario and a hand-derived expectation first; engine output is never pasted into `expected.json`.

The forecast fixtures follow the same method (`tests/fixtures/forecast`: one 2 parcels x 2 zones x 1 service x 0 % residential x single package grid on the `standard` schedule, derived by hand from RULES.md, the pricing fixtures and design section 7, independent of `src/engine/forecast`). One expectation changed before the test was written: the first draft applied the free allowance to the expected number of inserts (0.4 x 4 = 1.6) instead of to the number on a qualifying order (4), which understated the charge; the corrected reading is in the fixture's `_ambiguities`.

### Forecasts from assumptions (`src/engine/forecast`)

`evaluateForecast(assumptions, deps, options)` prices what a brand describes instead of an orders file. The answer is an expected value over the mix described, never a prediction for a month and never an invoice.

* **Inputs** (`ForecastAssumptions`, version 1, hashed over canonical JSON): `monthlyOrders` (a whole number, 1 to 5,000,000), `asOfDate`, `originZip`, up to 14 `parcels` (weight, optional dimensions all-or-none, packaging type or unknown, share, optional "I don't know the size"), up to 30 `zones`, up to 10 `services`, `residentialPct`, `multiPackage {pct, packagesPerOrder 2-10}`, `content` (up to 12 `{units, lines, sharePct}` rows, or `averageUnits` and `averageLines`), and `fulfillment` (the same answers as a run). Every distribution adds up to exactly 100.00 (never normalised for the user; "spread evenly" is an explicit button). Rows are put in canonical order, so shuffling them changes nothing, byte for byte.
* **Grid:** one cell per parcel x zone x service x residential split x package class, at most 1,500, each weighted by monthlyOrders x the product of its shares in 60-digit exact decimals; the weights sum to `monthlyOrders` exactly.
* **Shipping:** each cell is priced once with `calculateShipment`, every input flagged assumed (residential, origin, weight, dimensions), so every counted shipping line is an estimate and `shipping.definite` is `0.00`. Cells are priced by zone, not by a ZIP. (The engine can price a zone with a representative ZIP supplied through `deps.destinationZipForZone`, which must resolve to that zone, but the application never supplies one: every forecast the app makes is priced by zone.)
* **Fees:** per content row and cell, the fee engine prices one order: the row's units and lines (distinct products taken as the number of lines), k identical packages of the parcel's packaging type, one shipment, the cell's shipping as the percent base, with every quantity flagged assumed (so every order line is an estimate). Averages are split two-point (1.4 items is 60 % of orders with 1 and 40 % with 2) and coupled so lines never exceed items.
* **Aggregates:** the sum of weight x amount, rounded once per reported figure (E4, then cents). Monthly charges, one "average" month bucket for the minimum (fraction 1), the allocation and the all-in come from the same engine functions as file runs; the all-in appears only when every rate-bearing category is priced and every cell was priceable.

**Carve-outs** (what a forecast does differently from a file run, and what it leaves out):

1. Nothing a forecast prices is definite. The one exception is a flat `month` rule, which stays definite (it rests on no assumption).
2. Delivery-area and remote-area surcharges depend on the destination ZIP, which a forecast does not have: they are reported as "could not be decided (up to $X a month)" and never added, and post-shipment exposure (address corrections) is shown as an upper bound. (An engine caller that supplies a representative ZIP per zone would price that one ZIP's surcharges for the whole zone; the application does not.)
3. Every order ships as one shipment of one package, or of k identical packages for the multi-package share; the choices (parcel, zone, service, home or business, packages, content) are treated as independent. No signature, Saturday delivery or declared value.
4. Order-share drivers are expected values: a qualifying order is charged max(0, count - allowance) x rate and the expectation is share x that amount ("40 % of orders get 4 inserts, the first free" costs 0.40 x 3 x $0.25 = $0.30 per order). Every order is priced as ordinal 10,000, which qualifies for any share that is a whole number of hundredths of a percent, and the result is scaled by the share.
5. If some cells cannot be priced (a service x zone the rate card does not cover) the save is blocked with a table of what is missing; "price only what the rate card covers" averages over the priced volume only, imputes nothing, and shows no all-in figure or projection (the minimum is then an upper bound).
6. The volume sensitivity (0.5x, 1x, 2x, 4x) holds per-order shipping and fees constant, scales the monthly charges that follow volume (a returns rate), and evaluates an exact account minimum again at each volume; price breaks that depend on volume are not re-read.
7. "Every order on service S" and "packaging X instead of Y" variants are **not built**, and no forecast can be built without a brand record.

## Carrier adapters

`src/engine/carriers/index.ts` holds **structure only**: how a carrier rounds and measures (offered as *structural defaults* when a 3PL sets up service terms, labelled "verify against the carrier's current service guide"), the evaluation order of surcharge categories, and the known mutually exclusive groups for the rule editor's guidance. No amounts, divisors or ZIP lists live there. The engine reads only `ServiceTerms`, so a 3PL can override every structural default per service.

## Data the engine receives

* `RateCardSnapshot`: one active version (services with DIM rules, minimum charge, included/excluded surcharge keys, zone-chart key, markup; rate rows; zone charts). Built by `src/lib/pricing/snapshot.ts` under the caller's Row Level Security, so a brand user can only ever load cards assigned to their brand and only the services allowed for them.
* `SurchargeRule[]` and `ZipList[]`: from `pricing_rules_for_card()`, a database function that authorizes once (staff of the tenant, or a brand with an active assignment) and returns the published or retired rule versions in force on the ship date for the card's carriers (platform scope plus the tenant's, limited for a brand to tenant-wide rules and rules scoped to that brand) and the ZIP-list versions those rules reference, in force on the date. Malformed rule conditions are rejected at load time and reported, never guessed.
* `SurchargeOverride[]`: the brand's live exceptions (the database allows at most one per rule on any date).

## Rate-card import (`src/lib/import`)

CSV/XLSX → tables (`parse-table.ts`, 5 MB, 50,000 rows and 600,000 cells per sheet caps; type sniffing) → detection (`rate-card-mapping.ts`: header synonyms for the long layout, grid layout detection, service-name suggestions with confidence; **heuristics only, no AI; the administrator approves**) → validation (`rate-card-validate.ts`: strict numeric parsing, bracket derivation and overlap/duplicate/gap checks, zone and origin formats, unmapped services, decreasing-price warnings, per-service coverage summary) → draft version with rows and service terms → activation with effective dates (two active versions can never overlap; enforced by a database exclusion constraint).

## Testing

* `tests/unit/engine-golden.test.ts`: 32 scenarios against `tests/fixtures/pricing/expected.json`, whose values were derived **independently of the engine** by two separate computations (one scripted, one by hand) from the design document and the fixture files, then reconciled. Two deliberate post-reconciliation decisions are recorded in the file (fuel on an estimated base is estimated; a counted line from an unverified rule is estimated).
* `tests/unit/engine-*.test.ts`: per-area tests (dimensional weight and rounding, zones and brackets and unavailable paths, surcharge semantics, money and validation) with hand-derived expectations, plus two adversarial review suites (`engine-numerics-review`, `engine-semantics-review`) written by reviewers who were asked to break the engine; each of their findings is now a passing test.
* `tests/unit/import-pipeline.test.ts`: parsers, mapping heuristics, validation.
* `tests/unit/orders-import.test.ts`: order-file detection and validation against generic, Shopify and ShipHero-style fixtures (counts of rows, orders, shipments, packages and lines derived by hand).
* `tests/unit/engine-throughput.test.ts`: 2,000 varied shipments on the fixture context stay under 10 ms each (measured ≈0.6 ms).
* `tests/db/pricing.test.ts`: who can see and change pricing data (RLS), activation/publication state machines, audit.
* `tests/unit/fees-golden.test.ts` (35 tests against `tests/fixtures/fees`), `forecast-golden.test.ts` and `forecast.test.ts` (golden grid, weights summing to the volume, row-shuffle invariance, nothing definite, allocation identity), `fees-schema.test.ts`, `modeling-fold.test.ts` and `modeling-finalize.test.ts` (fold v2 and the summary), `modeling-fee-input.test.ts` (order content and apportionment), `modeling-assumptions.test.ts`, `calculator-fees.test.ts`; `tests/db/fees.test.ts` for the SQL side (see TESTING.md for counts).

All fixture data is fictional and must never be shown as real pricing.

## Not implemented yet

Reweight/remeasure adjustment risk (5; a correction will be defined as calculate(corrected) − calculate(original) plus any correction-fee line), metric units, non-US destinations, carrier-published rule monitoring (8). Fulfillment fees and forecasts from assumptions exist since Milestone 4 with the limits stated in *Fulfillment fees* above and in IMPLEMENTATION_STATUS.md (seasonal windows, weight- or value-based handling fees, discounts, fees on fees, inventory dimensions, peak-based storage, nested minimums, per-receipt sizes, return postage, forecast variants and spreadsheet import of fee schedules are not modeled). Platform-scope (carrier-verified) rules can only be inserted by the service role today; the review/approval workflow arrives in Milestone 8. Out of scope by decision: volume-tiered products (USPS Cubic) and packaging-keyed rows (flat-rate boxes); rate cards are weight-bracketed only and the importer treats everything as weight brackets, so such sheets must not be imported until a `bracket_basis` is added.
